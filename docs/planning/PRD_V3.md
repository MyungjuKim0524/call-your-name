## 3. P0 기능 요구사항 및 인수 기준

### F01 콘텐츠·큐시트
- CAT-01: 음원, 캐릭터, 무대, 의상(구현된 경우), 안무, 조명, 효과의 안정적 ID·버전·활성 상태 및 권리 정보를 관리한다. **AC:** 미공개/권리 미확인/없는 자산은 공연 게시 불가.
- CAT-02: 공개 버전은 불변 스냅샷으로 보관한다. **AC:** 신규 버전 공개 후에도 기존 예약 공연의 버전은 변경되지 않는다. 권리 철회 시 기존 버전도 재생을 차단하고 안내한다.
- CAT-03: 큐시트는 audio_id, duration_ms, ordered cues(time_ms, action, asset_id, params)를 갖는다. **AC:** 음수·음원 길이 초과·허용되지 않은 효과·존재하지 않는 자산·호환되지 않는 캐릭터 조합을 서버가 거절한다. 동일 시각 충돌은 명시적 순서 규칙으로 처리한다.
- CAT-04: 간단한 구간별 편집·미리보기·오류 표시를 제공한다. 전문 영상 편집기 제외. **AC:** V2 엔진에서 저장된 큐시트를 재생할 수 있고 사용자 중단/음소거/모션 감소가 작동한다.

### F02 프리셋
- PRE-01: 검증된 큐시트를 익명 소유 자격과 연결해 저장·조회·수정·삭제한다. **AC:** 타 세션의 수정·삭제는 거절; 직접 ID 접근도 검사.
- PRE-02: 공개 링크는 추측하기 어려운 별도 식별자로 읽기 전용 공유. **AC:** 비공개·삭제·철회된 프리셋 열람 불가; 링크는 쓰기 권한을 부여하지 않으며 이름·고민·AI 원문을 포함하지 않는다.
- PRE-03: 버전 충돌을 탐지한다. **AC:** 오래된 버전으로 갱신 시 409 등 명시적 오류; 유효한 최신 버전을 다시 조회 가능.

### F03 공동 콘서트
- CON-01: 게시된 공연 버전과 서버 UTC 시작/종료 시각을 기준으로 동일 공연을 재생한다. **AC:** 두 브라우저가 동일 버전과 시점을 조회하며 늦게 입장해도 현재 재생 위치로 이동한다. 사용자 동작 후 오디오 시작.
- CON-02: REST 스냅샷 및 SSE로 상태를 전달한다. **AC:** 연결 끊김 후 재접속 시 스냅샷으로 최신 상태 복구; 역순·중복 이벤트로 상태가 후퇴하지 않는다. heartbeat 및 연결 종료 자원 회수.
- CON-03: 브라우저의 오디오 시간 기준으로 큐를 실행한다. **AC:** 재생 오차를 측정하고 Phase 0 승인 목표와 비교; 네트워크 지연/백그라운드 탭/음원 로딩 실패를 표시·복구한다. 실시간 오디오 스트리밍 구현 아님.
- CON-04: 예약 공연은 유효 입장권 검증을 요구한다. **AC:** 예약 취소·미예약 사용자의 REST 참여 및 SSE 구독 차단; 자유 관람은 기존 익명 세션으로 이용 가능.

### F04 공동 응원
- CHR-01: REST 응원은 서버에서 공연 상태·참가 자격·요청 제한·멱등 키를 검사한다. **AC:** 동일 키/동일 요청 재시도는 한 번만 반영; 키 재사용과 다른 payload는 충돌 처리.
- CHR-02: 응원 기록, 카운트 및 목표 달성 이벤트를 동일 DB 트랜잭션으로 처리한다. **AC:** 실제 PostgreSQL 병렬 요청에서 승인된 고유 응원 수와 카운트 일치, 롤백 시 모두 미반영, 목표 달성 논리 이벤트는 한 건.
- CHR-03: 커밋 후 Redis Pub/Sub → 각 서버 SSE 전달. **AC:** 두 로컬 서버에서 동일 이벤트 수신; 발행 실패/중복/역순 상황에서도 DB 스냅샷으로 수렴. Pub/Sub은 영속 큐가 아니다.
- CHR-04: 목표 달성 시 선택적 시각 효과 제공. **AC:** 같은 이벤트 ID로 화면 연출 반복 방지, 모션 감소·음소거 설정 준수. 공개 쓰기 제한 실패 시 안전하게 거절.

### F15 무료 티켓팅 (P0)
- TKT-01: 관리자가 자유 관람/예약 공연 구분, 예약 시작·종료, 공연 일정, 정원을 설정한다. **AC:** 잘못된 시간 순서·정원 값 차단; 예약이 존재하는 공연의 정원을 활성 예약 수 아래로 낮추지 못한다. 변경 정책은 Phase 0 승인.
- TKT-02: 익명 서버 세션으로 무료 예약을 생성한다. 한 공연에 한 활성 예약을 기준안으로 한다. **AC:** 예약 가능 기간과 정원이 유효할 때만 성공; 중복 클릭/재시도는 중복 재고 차감 없음. 정원 소진 시 명확한 응답과 다른 공연 선택 제공.
- TKT-03: 예약과 재고 변경은 하나의 PostgreSQL 트랜잭션이다. **AC:** 정원 C, 서로 다른 N>C 요청의 로컬 경쟁 테스트에서 활성 예약은 C 이하이고, 충분한 유효 요청이 성공한 조건에서 C와 일치; 잔여 정원=정원-활성 예약. 실패·롤백은 차감하지 않는다. Redis는 재고 원본으로 쓰지 않는다.
- TKT-04: 소유자만 예약 취소 가능하며 정원 반환은 한 번만 수행한다. **AC:** 중복 취소, 예약/취소 동시 실행, 마감 시각 경계, 취소 후 재예약 정책 검증. 취소 가능 시각과 재예약 허용 정책은 Phase 0에 사용자 승인.
- TKT-05: 입장 시 서버가 공연 ID·활성 예약·익명 소유권·입장 가능 시각을 확인한다. **AC:** 다른 세션/다른 공연/취소 예약/변조 ID로 입장 불가; 유효 예약의 재연결 가능. 입장권은 양도하지 않으며 공유 링크가 입장 자격을 부여하지 않는다.
- TKT-06: 예약 현황 및 예약 성공/실패/취소 상태를 화면에서 확인한다. **AC:** 서버 응답 전 성공 표시 없음, 클라이언트 잔여석은 안내 값이며 실제 예약 판단은 트랜잭션 기준. 개인정보·실명·결제 정보 수집 없음.
- TKT-07: 정원 변경, 예약/취소/입장, 공연 종료 및 요청 제한에 대한 관리자 감사 로그 및 테스트. **AC:** 로그에 토큰/세션 원문 없음, 동시에 응원과 예약 요청이 들어와도 각 불변식 유지.

### F05 AI 연출 Agent
- AI-01: 사용자는 공연 콘셉트만 입력한다. Spring이 길이·요청 제한을 검사하고 FastAPI에 인증된 요청을 전달한다. **AC:** AI 비가용·무료 한도 초과·timeout에도 수동 공연 사용 가능.
- AI-02: LLM은 읽기 전용 카탈로그 도구를 사용하고 제한된 JSON 구조를 반환한다. **AC:** 도구 allowlist, 호출 횟수/시간/출력 크기 제한; 임의 외부 접근이나 쓰기 도구 없음. 프롬프트 인젝션에도 정책 변경 불가.
- AI-03: FastAPI 스키마 검증 후 Spring이 자산 존재·공개·권리·타임라인·호환성 재검증. **AC:** 잘못된 JSON, 가짜 ID, 길이 초과, 미공개 자산, 철회 버전 모두 실행/저장 차단. 필요 시 제한된 수정 재시도 후 기본 프리셋 제공.
- AI-04: 사용자가 결과를 미리 보고 수정·승인해야 저장한다. **AC:** AI 자동 게시·자동 실행 없음. 개인 이름·고민·편지 내용은 전달하지 않음. 원문 프롬프트 기본 미저장; API 키 서버 전용.
- AI-05: 평가셋과 모델/프롬프트 버전, 유효 출력률, 자산 정확성, 시간 제약, 의도 반영, 응답 지연, 실패 유형을 기록한다. **AC:** 정상·모호·공격·없는 자산·한도 초과 케이스 포함, 동일 조건 비교, 실제 결과만 기록. 임계값/표본 수 Phase 0 승인.

### F06 운영자 도구
- ADM-01: 기존 V2 인증 재사용 여부 검증, 관리자 역할과 일반 익명 이용 구분. **AC:** 직접 API 호출에도 인가 적용, 세션/CSRF 정책 확인.
- ADM-02: 카탈로그·공연 버전 검증/공개와 일정·정원 관리만 우선 구현. **AC:** 비관리자 게시 금지, 참조 중인 버전의 무단 변경 방지, 관리자 변경 감사 기록. 기존 병편지 검수 기능 회귀 없음. 범용 CMS 제외.

### F13 엔지니어링 / F14 Kafka 문서
- ENG-01: Docker 로컬 재현, GitHub Actions 테스트 및 배포 게이트, 환경변수·시크릿 분리, 헬스체크와 구조화 로그. 무료 플랜 한도/자동 과금 설정을 직접 확인한다.
- ENG-02: 실제 DB·Redis 통합, 프론트 회귀, 보안·동시성·SSE 부하·SQL 실행계획 실험을 수행한다. 합성 데이터와 운영 데이터 분리.
- ENG-03: V2 회귀와 권리·보안·무결성 출시 게이트를 통과해야 공개한다. 미완료 기능은 비활성화한다.
- KFK-01: `docs/design/FUTURE_KAFKA_ARCHITECTURE.md`에 도입 조건, Outbox/relay, Topic·partition key·consumer group, 이벤트 envelope, 멱등성, retry/DLQ, lag, 재처리, 마이그레이션·롤백, Redis Streams/RabbitMQ 비교, 검증 계획을 작성한다. **AC:** 기획서 §8과 일치하고 ADR 및 backlog 링크 존재. Kafka 설치·라이브러리·코드·배포·테스트 없음.

## 5. 데이터 모델 설계 초안

기존 V2 테이블과 충돌 여부를 Phase 0에서 확인하고 Flyway 증분 마이그레이션을 작성한다. 아래는 논리 모델로, 물리명과 타입은 구현 설계 시 확정한다.

| 엔티티 | 주요 속성 | 제약 및 책임 |
|---|---|---|
| content_asset / asset_version | id, kind, version, status, rights_status, metadata | 안정적 ID, 버전 유일성, 게시 권리 검증 |
| cue_sheet_version | id, audio_version_id, duration_ms, cues, version | 게시 버전 불변, 참조 검증; JSONB 후보 |
| preset | id, owner_subject_id, sheet_version_id, share_id, visibility, version | 소유권, 공유 ID UNIQUE, 낙관적 버전 검증 |
| concert | id, sheet_version_id, starts_at, ends_at, admission_mode, status | 시간 순서, 게시 버전 참조 |
| concert_inventory | concert_id, capacity, reserved_count, booking_opens_at, booking_closes_at | PK/FK, CHECK 0 <= reserved_count <= capacity; 예약 공연 전용 |
| ticket_reservation | id, concert_id, subject_id, status, created_at, cancelled_at | FK, 공연·주체별 활성 예약 유일성; 취소 이력 유지 |
| idempotency_record | subject_id, operation, key, request_hash, result | 복합 UNIQUE, 요청 해시 일치, 업무 트랜잭션과 원자성 |
| cheer_state | concert_id, count, target, version | 비음수·단조 버전, 공연별 단일 행 |
| cheer_event | id, concert_id, subject_id, request_key, occurred_at | 중복 방지, 카운트와 동일 트랜잭션 |
| milestone_event | id, concert_id, milestone_id, state_version | 공연·목표 UNIQUE, 논리 이벤트 한 건 |
| anonymous_session | subject_id, credential_hash, expires_at | 토큰 원문 저장 금지; 만료·회전 정책 |
| admin_audit | actor_id, action, resource_id, outcome, occurred_at | 민감정보 제외, 접근 제한 |
| analytics_event (P1) | event_id, kind, content_id, occurred_at | 허용 이벤트만, 중복 제거, 개인정보 최소화 |

### 티켓팅 트랜잭션 기준

1. 서버 기준 세션·공연·예약 가능 상태 확인. 재시도 키는 주체/작업 범위에서 검증한다.
2. 동일 공연 재고 행을 `SELECT ... FOR UPDATE`로 잠그거나 `reserved_count < capacity` 조건의 원자 갱신을 사용한다. 두 방식을 실측 비교할 수 있으나 최종 구현은 하나를 선택하고 ADR에 기록한다.
3. 잠금 획득 후 시간·정원·활성 예약 조건을 재검증하고 예약 및 재고 갱신을 같은 트랜잭션에서 커밋한다. 일관된 잠금 순서 사용. UNIQUE 위반과 교착/timeout은 명확한 실패 또는 제한된 재시도로 처리한다.
4. 취소는 활성 상태에서만 조건부 변경 후 재고 반환. 상태 변경과 반환은 하나의 트랜잭션이며 중복 취소는 재차 반환하지 않는다. 예약/취소/정원 변경의 잠금 순서 일치.
5. 응원 트랜잭션과 예약 트랜잭션의 책임 분리. Redis 장애가 정원을 바꾸어서는 안 된다. 실제 DB 조회로 불변식 검증. 임의의 대량 부하를 운영 서비스에 가하지 않는다.

## 6. API 계약 초안

SSE 이벤트 예시: `state`, `cheer.updated`, `milestone.reached`, `concert.ended`, 각 이벤트의 concert_id·state_version·event_id 포함. 재연결 시 DB 스냅샷을 기준으로 복구한다.
